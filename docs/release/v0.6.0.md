# VECTIS v0.6.0

VECTIS 0.6.0 adds first-class explicit actions so external work can participate in the execution graph without weakening the separation between deterministic computation and runtime authority.

## Action syntax

```vectis
action response "http.request" using "http" {
    method: "GET",
    url: endpoint
};
```

An action binds its result, names the external operation, names the capability required to run it, and supplies deterministic structured input.

## Graph and runtime

Action input references become ordinary dependency edges. The compiled action node records operation, capability, canonical input expression, stage context, and source-expression evidence.

Runtime execution requires both a granted capability and an operation registered through `ActionRegistry`. The registry permanently associates each operation with one capability, so source cannot relabel an operation to acquire different authority.

Missing capability grants, unavailable operations, capability mismatches, invalid object input, adapter denials, adapter timeouts, and invalid action result values fail closed.

## Standard bindings

The registry can bind the existing bounded adapters:

1. `filesystem.read_text`
2. `filesystem.write_text`
3. `process.run`
4. `http.request`

Filesystem roots, process executable allowlists, process environment, HTTP transport constraints, and timeout ceilings remain configured by the embedding application.

## Result flow

Action results remain VECTIS values. A result can feed later actions, assertions, conditions, pure expressions, publications, reports, and Mission Control inspection.

## Dry run

Dry-run execution preserves deterministic scheduling and action-node visibility without calling external handlers.

## Compatibility

Existing 0.2 through 0.5 source remains valid under the 0.6 contract except for identifiers that collide with the newly reserved `action` and `using` keywords.

The operation-to-capability binding and fail-closed action runtime are compatibility commitments for the 0.6 patch line.

## Design record

RFC 0003 documents the action syntax, semantic model, graph representation, runtime rules, authority boundary, determinism limits, failure behavior, alternatives, and test strategy.

## Verification

Release verification covers parsing, formatting, semantic input validation, graph dependency creation, capability enforcement, unavailable-operation failure, capability mismatch rejection, result propagation, bounded filesystem action integration, dry-run behavior, repository policy, package build, isolated-wheel checks, and Python 3.11 through 3.14.
